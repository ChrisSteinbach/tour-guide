# Spherical Nearest-Neighbor Search

WikiRadar's nearest-neighbor search is built on the [`spherical-delaunay`](https://github.com/ChrisSteinbach/spherical-delaunay) npm package: spherical Delaunay triangulation computed as a 3D convex hull, with nearest-neighbor queries answered by triangle walks on the resulting mesh. The core theory — why convex hull equals spherical Delaunay, the build and query algorithms, and why this approach was chosen over alternatives like KD-trees or hierarchical point location — is maintained canonically in that package's own [`docs/nearest-neighbor.md`](https://github.com/ChrisSteinbach/spherical-delaunay/blob/HEAD/docs/nearest-neighbor.md), so the two documents don't silently drift apart. This document instead covers **how WikiRadar integrates and applies it**: the `NearestQuery` adapter, tile-patch queries, cross-tile merging, binary tile-format integration, and the X-ray walk trace.

## How WikiRadar uses it

The pipeline calls `convexHull()` then `buildTriangulation()` once per tile (`src/pipeline/build.ts`; see [tiling.md](tiling.md)), producing a triangulation that `serializeBinary()` writes into each tile's `.bin` file. At runtime the app calls `deserializeBinary()` to get a flat `FlatDelaunay` and queries it directly — no object-graph conversion needed.

`src/app/query.ts` is a thin adapter over the package: its `NearestQuery` class wraps `createQueryContext`/`findNearestVertices` and maps each vertex index to a _group_ of articles rather than a single one — distinct Wikipedia articles can share bit-identical coordinates (e.g. a building and the institution sited in it) and collapse to one triangulation vertex, so the group travels together, ordered most-notable-first. A vertex's max weight (`group[0]`) is what the `minWeight` option filters on when it becomes a vertex predicate; a hit against that vertex then expands into one result per co-located article — title, weight class, and the vertex's shared distance in meters — dropping any article that individually falls below `minWeight`. Internally, a query is a triangle walk (O(√N) expected steps) to locate the containing triangle, a greedy descent through Delaunay neighbors to the nearest vertex, and — for `k > 1` or a filtered query — a BFS expansion collecting `max(2k, k+6)` candidate vertices. See the package's own docs for how each step works.

## Tile patches: why the runtime walk is hardened

A tile's vertices cover only a ~5.5°×5.5° patch of the sphere (the 5° grid cell plus its 0.5° buffer — see [tiling.md](tiling.md)), so their convex hull is a thin lens. The hull's topside facets are the true spherical Delaunay triangles of the patch, but the hull is closed by "back-closure" facets spanning the rim. As spherical regions for the walk's edge tests, topside facets cover the patch while back-closure facets cover its _antipode_ — so a query outside the patch (the app queries adjacent tiles with such positions on every update) is contained by **no facet at all**. The textbook walk can never terminate by containment there: it orbits the back closure for thousands of steps until cycle detection or the step limit rescues it, then seeds the descent from an arbitrary triangle.

Two data artifacts compound this. Float32 coordinate quantization (the binary tile format — see [binary-format.md](binary-format.md)) collapses co-located articles onto identical coordinates, producing degenerate zero-area triangles whose edge-test signs are noise, and clusters whose inner vertices have no strictly-closer neighbor — a greedy descent arriving from far away can stall in such a pocket kilometres from the true nearest. (Before hardening, ~3% of single-tile queries in a Stockholm-area sweep returned results up to 580 km off; the multi-tile merge in `findNearestTiled` masked this in practice.)

`spherical-delaunay` hardens the walk against exactly this. The full mechanism — best-seen tracking, patience termination, back-closure walls, anchor restart, cycle triage, and plateau tunneling for quantization pockets — is documented in the package's own [`docs/nearest-neighbor.md`](https://github.com/ChrisSteinbach/spherical-delaunay/blob/HEAD/docs/nearest-neighbor.md#patch-triangulations-why-the-runtime-walk-is-hardened). One detail worth calling out here: the back-closure walls also keep tile-wide chord streaks out of the X-ray walk trace (the animated triangle-walk overlay in the browse map's X-ray panel — see the [README](../README.md#x-ray-mode)), since a walk free to cross into back-closure facets would otherwise draw long spurious hops straight across the tile.

With hardening in place, a 9,240-query sweep over seven production tiles (in-patch and out-of-patch positions) matches brute force exactly, with walks averaging ~150–225 hops and bounded by ~520 — versus averages of 10k–18k hops, frequent O(V) brute-force fallbacks, and 268 wrong results for the textbook walk.

## Cross-tile merging

A single tile only covers its own patch, so `findNearestTiled()` in `tile-loader.ts` queries every loaded tile's `NearestQuery` independently, de-duplicates candidates by title, sorts by distance, and returns the top `k`. See [tiling.md](tiling.md#cross-tile-query-merging) for the implementation and [architecture.md](architecture.md) for where this sits in the end-to-end query path.

## Distance computation

`NearestQuery` reports distances in meters using chord distance (`2 * asin(||v - q|| / 2)`), which `spherical-delaunay` computes instead of `acos(dot(a, b))` specifically because tile vertex coordinates come from Float32 storage in the binary tile format (see [binary-format.md](binary-format.md)) — `acos` collapses to 0 under Float32 rounding error for nearby points, while chord distance stays above the noise floor. Both are monotonically related to great-circle distance, so nearest-neighbor ordering is unaffected.

## Why this approach

With tiling (N ≈ 1,500 per tile — see [tiling.md](tiling.md)), the triangle walk takes on the order of √N ≈ 39 steps per tile. See `spherical-delaunay`'s [`docs/nearest-neighbor.md`](https://github.com/ChrisSteinbach/spherical-delaunay/blob/HEAD/docs/nearest-neighbor.md#why-this-approach) for the comparison against KD-trees and hierarchical point location that motivated choosing triangle walks in the first place.
